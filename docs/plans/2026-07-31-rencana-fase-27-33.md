# FASE 27 — Validasi body HTTP

> **STATUS: SELESAI 2026-07-31.** Seluruh 64 titik `@Body()` tanpa DTO class
> di 13 controller sudah diberi DTO + dekorator `class-validator`. Field
> keamanan attachment (`scanStatus`/`mimeDetected`/`checksum`/`byteSize`, T-05)
> dihapus dari DTO klien, server yang menentukan. Verifikasi:
> `Get-ChildItem apps\api\src -Recurse -Include *.controller.ts | Select-String
> -Pattern "@Body\(\)\s*\w+:\s*(Omit<|Partial<|Pick<|Record<|\{)"` → nol hasil.

**Menutup**: T-04 (64 titik `@Body()` tanpa DTO), T-15 (README salah).
**Prasyarat**: tidak ada. **Butuh keputusan manusia**: tidak.

## Tujuan

Setiap `@Body()` di `apps/api` memakai class DTO dengan dekorator
`class-validator`, sehingga `ValidationPipe` yang sudah aktif benar-benar
memvalidasi.

## Mengapa ini pertama

Karena `whitelist: true` + `forbidNonWhitelisted: true` sudah aktif di
`apps/api/src/bootstrap.ts`, tetapi tidak punya apa pun untuk divalidasi. FASE 28
bergantung pada ini: melarang klien menetapkan `scan_status` tidak ada artinya
kalau body-nya sendiri tidak divalidasi.

## Langkah

1. **Catat baseline.** Jalankan dan simpan angkanya:

   ```
   cd D:\Games\Agent\Chai
   pnpm run test          2>&1 | Select-Object -Last 15
   pnpm --filter @chai/api run test:integration 2>&1 | Select-Object -Last 15
   ```

2. **Dapatkan daftar titik yang harus diperbaiki.** Jangan percaya angka 64 di
   dokumen ini, hitung sendiri:

   ```
   Get-ChildItem apps\api\src -Recurse -Include *.controller.ts |
     Where-Object { $_.FullName -notmatch '\\node_modules\\' } |
     Select-String -Pattern "@Body\(\)\s*\w+:\s*(Omit<|Partial<|Pick<|Record<|\{)" |
     ForEach-Object { "$($_.Path):$($_.LineNumber)" }
   ```

3. **Tiru pola yang sudah benar.** Baca `apps/api/src/auth/auth.dto.ts` — itu
   satu-satunya DTO yang ada dan menjadi acuan gaya.

4. **Kerjakan SATU controller per commit**, mulai dari yang paling kecil supaya
   polanya mantap dulu: `notification` (2 titik) → `template` (2) →
   `contact-segment` (2) → `attachment` (2) → `campaign` (3) → `ticket` (3) →
   `sla` (4) → `ai-agent` (6) → `multi-region` (6) → `partner-ecosystem` (6) →
   `enterprise` (8) → `observability` (9) → `advanced-analytics` (11).

   Untuk setiap controller:
   - buat `<nama>.dto.ts` di folder modul yang sama;
   - satu class per operasi (`CreateXDto`, `UpdateXDto`);
   - beri dekorator sesuai tipe: `@IsString()`, `@IsInt()`, `@IsBoolean()`,
     `@IsIn([...])` untuk union literal, `@IsOptional()` untuk field opsional,
     `@ValidateNested()` + `@Type()` untuk objek bersarang;
   - ganti tipe di `@Body()` menjadi class DTO itu;
   - **jangan** ubah logika repository atau bentuk respons.

5. **Field yang tidak boleh diterima dari klien** — hapus dari DTO, jangan hanya
   ditandai opsional: `id`, `tenantId`, `createdAt`, `updatedAt`, dan setiap

   `scanStatus`, `mimeDetected`, `checksum`, `byteSize` — FASE 28 akan mengisinya
   di sisi server.

6. **Tulis test dulu untuk satu controller** sebagai bukti pola bekerja: kirim
   body dengan field asing, harapkan `400`. Tiru gaya `apps/api/test/*.e2e.test.ts`
   (ingat header `x-test-subject: local|client-owner`).

7. **Perbaiki README** (T-15): hapus `media` dan `Temporal` dari daftar worker,
   atau ganti dengan 7 worker yang benar-benar ada. Verifikasi dulu:

   ```

   ```

# FASE 28 — Keamanan attachment

> **STATUS: SELESAI 2026-08-01.** 28.A sudah ada sesi sebelumnya: server
> menetapkan `scanStatus: 'PENDING'` di `AttachmentController.create`, DTO tidak
> menerima `scanStatus`/`mimeDetected`/`checksum`/`byteSize`, dan unduh ditolak
> untuk `scanStatus != 'CLEAN'`.
>
> **28.B — keputusan diambil:** TIDAK memasang scanner virus eksternal (ClamAV
> dkk) — dependency infrastruktur besar di luar scope. Sebagai gantinya dibangun
> **MIME sniffing berbasis magic bytes, tanpa dependency**:
> `detectMimeFromMagicBytes(buffer: Uint8Array): string | null`
> (`packages/domain/src/attachment/mime-detection.ts`) — mengenali PDF, PNG,
> JPEG, GIF (87a/89a), ZIP (+varian kosong/spanned), plus heuristik teks ASCII;
> tanda tangan biner diperiksa sebelum heuristik teks (agar header "%PDF-" yang
> semuanya ASCII tidak salah dilabeli teks). Fungsi **berdiri sendiri, TIDAK
> disambung ke controller**: `AttachmentController` hanya menerima metadata
> (`objectKey`/`originalFilename`/`mimeDeclared`), tidak ada endpoint multipart
> yang membawa byte asli. Menyambungkannya sekarang hanya akan berpura-pura
> memvalidasi. Fungsi diexport dari `@chai/domain`, siap dipakai saat jalur
> ingest byte nyata ada (mis. worker media). Keterbatasan tercatat: karena byte
> asli tidak tersimpan, ketidakcocokan `mime_declared` vs hasil deteksi adalah
> SINYAL untuk scan manual, bukan penolakan otomatis.
>
> **Virus scan sungguhan: sengaja TIDAK ADA.** Attachment yang butuh scan virus
> tetap `PENDING` (karena itu tidak bisa diunduh) kecuali endpoint `POST :id/scan`
> manual (dari 28.A) dipanggil. Ini fitur mati yang disengaja dan aman (ponytail:
> keterbatasan, bukan bug).
>
> **28.C — test kontrak** (`apps/api/test/attachment.test.ts` +
> `packages/domain/src/attachment/mime-detection.test.ts`): (a) klien tidak bisa
> menetapkan `scanStatus` saat create — ValidationPipe menolak field non-whitelist
> + controller memaksa `PENDING`/null; (b) `PUT` tidak bisa mengubah `scanStatus`
> (termasuk `INFECTED → CLEAN`) — ValidationPipe menolak + controller
> mempertahankan status terminal; (c) unduh PENDING/INFECTED ditolak (sudah ada,
> tidak diduplikasi); (d) `detectMimeFromMagicBytes` mengenali tiap tanda tangan
> dan mengembalikan `null` untuk buffer tak dikenal/kosong/terpotong. Verifikasi:
> `@chai/api` typecheck+lint exit 0, `@chai/domain` typecheck+lint exit 0, unit
> test api 11/11 & domain 10/10 hijau. Tanpa migrasi — kolom `mime_detected` sudah
> ada di `0026_attachment.sql`.

**Menutup**: T-05 (kolom keamanan dikendalikan klien), T-10 (nol test keamanan file).
**Prasyarat**: FASE 27 selesai.
**Butuh keputusan manusia**: sebagian — lihat 28.B.

## 28.A — Server yang menentukan (kerjakan sendiri)

Setelah FASE 27, `scanStatus`/`mimeDetected`/`checksum`/`byteSize` sudah tidak
diterima dari body. Sekarang pastikan server yang menetapkannya:

1. Attachment baru **selalu** dibuat dengan `scanStatus: 'PENDING'`, ditetapkan di
   service/repository, bukan dari input.
2. `@Put(':id')` **tidak boleh** mengubah `scanStatus`, `mimeDetected`,
   `checksum`, `byteSize`. Transisi status hanya boleh lewat jalur internal.
3. Transisi yang sah: `PENDING → CLEAN`, `PENDING → INFECTED`, `PENDING → FAILED`.
   `INFECTED` dan `CLEAN` bersifat terminal — tolak perubahan dari keduanya.
   Ini invarian sejenis "`PAID` tidak pernah mundur" di README.
4. Akses unduh/pemakaian attachment dengan `scanStatus != 'CLEAN'` harus ditolak.

Test yang wajib ada (naikkan jumlah test):

- klien mengirim `scanStatus: 'CLEAN'` saat create → nilai tersimpan tetap `PENDING`;
- klien mencoba `PUT` mengubah `INFECTED` → `CLEAN` → ditolak;
- attachment `PENDING` tidak bisa diakses.

## 28.B — Scanner nyata (BERHENTI DAN TANYA)

Mengubah `PENDING` menjadi `CLEAN` memerlukan sesuatu yang benar-benar memeriksa
byte. Ini keputusan produk dan infrastruktur, bukan pilihan teknis kecil:

- Pakai scanner nyata (mis. ClamAV sebagai layanan) atau tidak?
- Kalau tidak ada scanner, apakah attachment tetap `PENDING` selamanya dan tidak
  pernah bisa diunduh? (aman, tapi fitur mati)
- Siapa yang melakukan MIME sniffing dan dari byte mana — apakah ada penyimpanan
  objek yang menyimpan byte aslinya?

**Jangan** menambah dependency scanner atas inisiatif sendiri. Tulis pertanyaan
di atas, laporkan, berhenti.

## 28.C — Test keamanan file (butuh 28.B diputuskan)

Blueprint 12 §12 menuntut: MIME spoof, malware, oversized, corrupt, archive
traversal, decompression bomb, SVG/HTML script, password-protected, SSRF URL,
redirect chain, timeout. Test ini hanya bermakna setelah ada jalur ingest byte
yang nyata (28.B). Sebelum itu, yang bisa ditulis hanyalah test kontrak 28.A.

## Verifikasi

Sama seperti FASE 27, ditambah:

```
Get-ChildItem apps\api\src\modules\attachment -Recurse -Include *.ts |
  Select-String -Pattern "scanStatus"
```

Pastikan penetapan `'PENDING'` ada di kode server, dan tidak ada jalur yang
menyalin `scanStatus` dari input.

**Menutup**: T-06. **Prasyarat**: tidak ada.
**BUTUH KEPUTUSAN MANUSIA — JANGAN DIKERJAKAN AGENT SENDIRI.**

## Mengapa berhenti

`workers/inbox-dispatcher/src/main.ts` sudah menjelaskan hambatannya di
komentarnya sendiri: `chai.inbox_event` hanya menyimpan `payload_reference` +
hash, sehingga tidak ada cara merekonstruksi event mentah. Komentar itu menulis
"Real async processing is BLOCKED on a restricted payload store".

Ini bukan pekerjaan yang bisa disimpulkan dari kode. Pertanyaan yang harus
dijawab manusia:

1. **Di mana payload mentah webhook disimpan?** Kolom `jsonb` di Postgres, atau
   penyimpanan objek dengan referensi?
2. **Berapa lama disimpan?** Payload berisi isi pesan pelanggan — ini data
   pribadi. Retensi harus disengaja.
3. **Apa yang diredaksi sebelum disimpan?** Blueprint melarang menyimpan
   kartu/CVV/PIN/OTP/kredensial bank.
4. **Apakah RLS berlaku?** Kalau payload masuk tabel ber-tenant, wajib RLS
   `ENABLE` + `FORCE` seperti invarian README.
5. **Siapa yang boleh membacanya?** Worker perlu akses, tetapi jangan sampai
   membuat jalur baca lintas-tenant.

Tanpa jawaban ini, FASE 30 dan 31 tidak bisa dikerjakan dengan benar.

- Ada test yang membuktikan event yang diterbitkan benar-benar diterima consumer.
- Test pengulangan event membuktikan idempotensi.
- `Select-String -Pattern "RedisStreamsConsumer"` menunjukkan pemakai produksi,

# FASE 31 — Pipeline balasan AI — **SELESAI (2026-08-01)**

> **STATUS: SELESAI 2026-08-01.** Keputusan arsitektur diterapkan: AI hanya membalas saat `conversation.mode === 'AI_ACTIVE'`, pesan AI dipublish sebagai `message.created` (bukan `message.received`, anti-loop), dan idempotency key `aiReplyExternalId(triggerMessageId)` digunakan di DB (`recordAiReply`). **Menutup**: T-01, T-02. **Prasyarat**: FASE 29 dan 30.
**BUTUH KEPUTUSAN MANUSIA — JANGAN DIKERJAKAN AGENT SENDIRI.**

## Mengapa berhenti

Ini gap terbesar dan paling menentukan bentuk produk. Yang sudah pasti dari
audit: `services/ai-gateway` lengkap (adapter model, guardrail, RAG, budget cap)
tetapi **nol paket mendeklarasikannya sebagai dependency**, dan tidak ada apa pun
yang memicu balasan otomatis.

Keputusan yang harus diambil manusia sebelum satu baris kode ditulis:

1. **Kapan AI membalas?** Setiap pesan masuk, atau hanya ketika percakapan dalam
   mode tertentu? README menyebut `conversation.mode` — mode mana yang
   mengizinkan AI dan mana yang murni manusia?
2. **Apakah balasan langsung terkirim atau menunggu persetujuan agen?** Ini
   menentukan apakah butuh antrean draft.
3. **Apa yang terjadi saat guardrail menolak?** Diam, atau eskalasi ke manusia?
4. **Batas biaya per tenant** — `budget.test.ts` sudah ada di ai-gateway, tetapi
   siapa yang menegakkannya di runtime dan apa yang terjadi saat plafon tercapai?
5. **Kanal mana yang aktif?** Membalas ke WhatsApp berbeda konsekuensinya dengan
   membalas ke widget web.
6. **Bagaimana mencegah loop** ketika balasan AI sendiri memicu event baru?

## Kerangka yang sudah tersedia (untuk dipakai, bukan dibangun ulang)

## Yang harus diputuskan manusia

Blueprint 11 minta 18 fact table dan 33 metrik. Membangun semuanya sekaligus
adalah pekerjaan besar dengan nilai tidak merata. **Tanyakan metrik mana yang
benar-benar dibutuhkan lebih dulu**, lalu bangun hanya fact yang menopangnya.

## Yang bisa dikerjakan tanpa bertanya

1. **Pertahankan `MetricLineage`.** Ini satu-satunya prinsip blueprint yang sudah
   terpenuhi ("denominator visible"). Setiap metrik baru wajib memakainya.
2. **Pisahkan penyimpanan analitik dari operasional.** Metrik tidak lagi query
   langsung ke `chai.conversation` / `chai.lead` / `chai.appointment`.
3. **Fact diisi dari event, bukan dari scan tabel operasional** — inilah sebabnya
   FASE 30 menjadi prasyarat.
4. `sourceUntil` yang dipatok `'2026-07-19T00:00:00.000Z'` di
   `InMemoryAnalyticsRepository` harus menjadi parameter, bukan konstanta.

## Aturan teknis

- Setiap fact table ber-`tenant_id` wajib RLS `ENABLE` + `FORCE` + policy
  `chai.current_tenant_id()` — pakai template di panduan bagian 0.3.
- Migrasi diawali `SET ROLE chai_migration_owner;` diakhiri `RESET ROLE;`.
- **Cek sendiri nomor migrasi terakhir**, jangan percaya angka di dokumen mana pun.
